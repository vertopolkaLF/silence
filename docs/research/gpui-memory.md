## Measurement boundary

The parent task supplied a release benchmark: one visible Material You/MicIcon overlay, no text or registered embedded fonts, private working set 18.53–18.71 MiB over 60.4 seconds. It also reported approximately 5 MiB before GPUI initialization. These are supplied measurements, not independently reproduced here. The goal is below 15 MiB **private working set**, not total working set or GPU allocation size. Raw texture byte counts below do not predict equal private working-set savings.

## Explanations to rule out

- **Runtime HLSL compilation is not the release startup cost.** `RawShaderBytes::new` uses embedded compiled bytes when `debug_assertions` is disabled. Runtime `D3DCompileFromFile` belongs to the debug path. The D3D debug layer is also disabled in that configuration. Driver shader creation may still allocate private resources; that is separate from HLSL source compilation. [Shader selection](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/directx_renderer.rs#L1745-L1775), [debug layer gate](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/directx_devices.rs#L76-L89).
- **`MAX_INSTANCE_BUFFER_SIZE = 256 MiB` is a cap, not an initial allocation.** Pipelines start at 4/16/32/64/512 instances and grow to fit used scene data. Removing the cap will not reduce the initial memory footprint. [Initial capacities](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/directx_renderer.rs#L942-L1022), [growth](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/directx_renderer.rs#L1130-L1160).
- **Changing the DirectWrite factory from shared to isolated is not a supported memory optimization.** Microsoft recommends the shared factory to reduce duplicated internal cached font state. GPUI already uses shared factories. [Microsoft guidance](https://learn.microsoft.com/en-us/windows/win32/api/dwrite/nf-dwrite-dwritecreatefactory).
- **Recreating overlays is not guaranteed to reclaim driver allocations immediately.** The pinned renderer's normal Drop only reports live objects in debug. D3D11 retains state-bound references and defers destruction; Microsoft documents releasing references followed by `ClearState` and `Flush` for synchronous destruction. This is relevant to the parent's repeated-theme recreation growth, but separate from the single-window fixed cost. Do cleanup only at teardown, not every frame: Flush has overhead. [Renderer Drop](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/directx_renderer.rs#L1284-L1291), [Microsoft teardown guidance](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-flush).

## Benchmark plan

Apply one experiment at a time to the same release scene and fresh process. Record private working set and private commit once per second for at least 60 seconds after first visible draw, with a separate startup peak and warmed median/range. Keep physical dimensions, monitor/DPI, muted state and GUI visibility identical. Confirm the overlay remains visible, alpha/click-through still work, and animation finishes normally. Avoid `EmptyWorkingSet` or periodic trimming: it changes residency without proving fewer allocated resources. If source-level reductions plateau above the target, capture allocation stacks/VMMap categories to distinguish Rust heap, DirectWrite and graphics-driver allocations before choosing a renderer replacement.

## Follow-up: defer the system font collection

The parent reports its combined experimental lazy-pipeline/lazy-emoji/128-atlas build reduced the icon-only private working set to approximately 17.7 MiB, with private commit approximately 63 MiB versus approximately 65 MiB. This follow-up measurement was not reproduced by this research task. Allocation groups of approximately 2.148 MiB and 3.16 MiB persisted; their ownership is not established from sizes alone.

`DirectWriteTextSystem::new` eagerly calls `GetSystemFontCollection(false, ..., true)` even without a single `font_id` request. The first flag excludes downloadable fonts; the final flag forces an immediate update check. Microsoft describes this method as retrieving the system font tree; using `checkForUpdates=false` skips the immediate check but still obtains the collection. Merely changing that flag is not equivalent to laziness. [Pinned construction](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/direct_write.rs#L196-L215), [Microsoft flags](https://learn.microsoft.com/en-us/windows/win32/api/dwrite_3/nf-dwrite_3-idwritefactory3-getsystemfontcollection).

The explicit field's other uses are font selection, a selection-miss refresh, explicit font fallback construction, and font-name enumeration. Glyph metrics/rasterization use already-selected font faces; text layout uses the selected font's own collection. The renderer's `get_font_info` obtains rendering parameters through the shared factory without requesting a system collection. Therefore deferring the collection until the first font selection/enumeration is compatible with an icon-only overlay. The size of any private RAM benefit is unverified. [Selection and refresh](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/direct_write.rs#L309-L360), [explicit fallbacks](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/direct_write.rs#L398-L454), [layout](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/direct_write.rs#L524-L568), [enumeration](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/direct_write.rs#L1285-L1293).

Minimal conversion design:

1. Store `system_font_collection: Option<IDWriteFontCollection1>` and initialize it to `None`.
2. Add a helper taking `&mut self` and components, returning `Result<IDWriteFontCollection1>`. Return a COM clone if cached; otherwise call `GetSystemFontCollection`, preserve its error with `?`, check the returned Option with context, cache only on success, and return a clone. Returning a clone avoids borrowing the field across mutations of font caches.
3. In `font_id`, upgrade the existing state lock, call the helper with `?`, then proceed with selection. This preserves an initialization error in the existing Result-returning API instead of replacing it with a missing-font panic. Selection can use the local collection clone; refresh stores `Some(collection)`.
4. Font-name enumeration needs a write lock to initialize. Its trait returns `Vec<String>`, so log helper errors and retain custom-font names; never unwrap failed initialization.

This smallest implementation still loads the collection when bundled fonts are first selected. A broader version can select from the custom collection first and initialize system fonts only after a custom-font miss or a nonempty explicit fallback list. `make_font_from_font_collection` currently requires the system collection argument even though it actually uses it only when constructing explicit fallbacks. An optional argument or a separated fallback construction step removes that dependency. Keep fallback ordering and refresh-on-miss behavior. DirectWrite may still initialize internal default fallback data while laying out text, so the icon-only result cannot be promised for bundled-text themes. [Custom-first selection](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/direct_write.rs#L320-L332), [fallback dependency](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_windows/src/direct_write.rs#L465-L520).
